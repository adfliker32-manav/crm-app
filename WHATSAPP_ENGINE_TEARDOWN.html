01 — System map

Everything hangs off one webhook and one send layer

The module looks like seven products but has exactly two doors. Everything inbound arrives at whatsappWebhookController; everything outbound leaves through whatsappService. Every subsystem in between is a consumer of the first and a caller of the second — none of them talk to Meta directly, and none of them talk to each other except through the conversation record.

02 — Inbound pipeline

What happens between Meta's POST and the customer's reply

This is a genuine sequence — each stage depends on the one before it, and a failure at any stage stops the ones after it. The numbering is the execution order, not decoration.

  1. Signature verification

    SHA-256 HMAC of the raw body against the app secret, compared with crypto.timingSafeEqual and a length guard. An unsigned or mismatched payload is rejected before anything is parsed.

    verifySignature() · whatsappWebhookController.js:109

  2. Immediate acknowledgement

    Meta gets 200 OK at once and the real work runs inside setImmediate. Meta retries any webhook it considers slow, so acknowledging late would duplicate every message.

    whatsappWebhookController.js:223

  3. Tenant resolution

    The incoming phone_number_id is matched to an active tenant. Everything downstream is scoped by the resolved id — there is no path that trusts a tenant id from the payload.

  4. Dual-key contact lookup

    Finds the Lead and the conversation by BSUID first, then phone suffix. BSUID is the durable identifier; as Meta rolls out usernames a contact may have no phone at all, which is why the lookup cannot be phone-only.

    whatsappWebhookController.js:813–866

  5. Atomic conversation upsert

    One findOneAndUpdate creates or updates the thread, increments unread and message counters, and re-activates archived threads. Concurrent inbound messages cannot create duplicates.

  6. Self-healing backfill

    Repairs the leadId link and re-derives the assigned agent on every inbound message. Strictly additive — null → a real link only, never a re-link, so a thread already owned by another Lead is never stolen.

    whatsappWebhookController.js:922–939

  7. Media mirroring

    Any image, video, document or audio is downloaded from Meta and mirrored to Cloudflare R2 under wa-inbound/<userId>/<mediaId>, because Meta's media URLs expire.

    inboundMediaService.js

  8. Routing

    The nine-stage ladder in the next section runs and selects exactly one owner for this message.

  9. Reply and fan-out

    The chosen owner composes a reply through the send layer, the message is persisted, and socket events push the thread into the right agents' inboxes in real time.

03 — Routing precedence

The ladder that decides who owns the message

This is the answer to "is there logic overriding anywhere". The router evaluates candidates in a fixed order and stops at the first match — so precedence is explicit, not emergent. The column that matters is the last one: three stages deliberately ignore the pause flag.

The single most important fact

The AI is last. It never competes with a flow — it only speaks when every scripted route has declined the message. A tenant who reports "the AI hijacked my chatbot" has a flow that stopped matching, not an AI that overrode one.

05 — Subsystem: flow chatbot

The scripted engine

A flow is a node graph stored on ChatbotFlow; a live traversal is a ChatbotSession holding the current node and a variable map. The engine walks nodes until it hits one that needs the customer, then parks.

Node types in play

Message, question, buttons, list, product/catalog, template, media request, delay, condition, action, AI, handoff, notify-agent and booking-link. Two carry state worth understanding:

  • Delay nodes schedule a job on Agenda (resume-chatbot-session) and can be set to cancel if the customer replies first — so a "wait 2 days then follow up" never fires at someone mid-conversation.
  • Question nodes can arm a no-reply timeout (CHECK_REPLY_TIMEOUT) that advances the flow when the customer goes quiet.

Miss handling

When a button or list reply cannot be matched, the engine re-prompts once, then hands that single turn to the AI in rescue mode — the session stays alive on its current node, so the flow resumes the moment the customer says something the node understands. Rescue turns are counted per session so a permanently broken node cannot burn a tenant's whole AI quota.

Smart Lead Engine

Per-flow lead qualification: rules combining minimum node interactions and required variables, producing a qualification level plus tags and a stage change. It runs on session progression, not on message receipt.

06 — Subsystem: AI chatbot

Three surfaces, one generator

Every LLM call in the module goes through aiService.generateReply, which returns a strict JSON envelope: reply, extracted_variables, and an optional action. What differs is where it is called from.

SurfaceFires whenSession?Actions handled
FallbackLadder stage 9 — nothing matchedNoAll six
RescueA flow node cannot parse the replyYes — stays activeAll six
In-flow AI nodeThe flow reaches an ai nodeYesFive of six

The six actions the model may request are change_stage, assign_tag, notify_agent, book_appointment, send_template and create_lead. The mismatch in the third row is a real defect — see finding W-1.

Lead creation policy

Recently added: IntegrationConfig.ai.leadCreation gives the tenant a server-enforced floor (minimum customer messages, required contact number / name / email) plus a plain-English instruction injected into the prompt. The gate is the authority — the model only asks, and a request that fails the policy is logged and dropped.

Design rule worth preserving

The LLM is never trusted with an irreversible decision. It proposes; the server disposes. Every action it can request is either idempotent (create_lead upserts) or gated server-side.

07 — Subsystem: knowledge base

Retrieval-augmented answers from the tenant's own documents

Tenants upload price lists, catalogues and FAQs. Files are parsed, chunked and embedded; at reply time the customer's message is embedded and the closest chunks are injected into the system prompt with strict instructions to quote only those figures.

The trap that already bit once

Cosine scores are not comparable across embedding models. A shared cut-off of 0.35 — correct for Gemini's compressed high band — silently returned nothing for every OpenAI tenant, while the document sat there showing "Ready". Each model now carries its own floor. Never reintroduce a shared default.

08 — Subsystem: templates

The 24-hour window is the whole reason this exists

Outside a 24-hour window from the customer's last message, Meta permits only pre-approved templates. Free text is rejected. Every scheduled or proactive send in the product therefore has to reason about which side of that window it is on.

Two guards before any template send

  • Language pair resolution. Meta identifies a template by (name, language). Asking for en_US against a template created as en returns error 132001 — "template name does not exist" — which reads like an approval problem and is not. The stored template row is authoritative, and {userId, name} is unique, so there is exactly one right answer.
  • Approval pre-check. checkTemplateSendable refuses anything not APPROVED. A template with no local row is treated as sendable rather than blocked, since it may simply be unsynced.

Template replies feed back into routing at ladder stage 5, including the case where the customer types "yes" instead of tapping a button — then the engine falls back to the last outbound template within the window, but only if no other inbound has arrived since, which together make the message unambiguously a reply to it.

09 — Subsystem: broadcasts

The only subsystem with its own queue infrastructure

Broadcasts are the one path that generates thousands of sends from a single click, so they get real queue machinery rather than a loop.

  • BullMQ on Redis, exponential backoff, worker concurrency 2 across all tenants — one tenant's blast cannot starve another's.
  • Jitter of 0–1000ms per batch, so parallel tenant broadcasts do not synchronise into a spike Meta reads as abuse.
  • Idempotency via a per-broadcast Redis set of already-sent leads (48h TTL). A worker crash and BullMQ retry cannot double-message anyone.
  • Cursor streaming over recipients rather than loading the whole audience into memory.

10 — Subsystem: inbox & assignment

Ownership is derived, never set

WhatsAppConversation.assignedTo is a read-only mirror of the linked Lead's owner. whatsappAssignmentService is its only writer; there is deliberately no API, request body or UI control that sets it independently. If the two ever disagree, the Lead wins and a backfill script re-derives the collection.

It is denormalised rather than joined because the inbox list, the unread badge and search all paginate and sort by lastMessageAt — a lookup would force a full-collection aggregation on every keystroke.

Real-time delivery

Conversation events go to a dedicated wa:<userId> socket room, never user:<id>. The reason is specific: join:company lets an agent into their manager's personal room, so filtering the emit loop alone would still leak every conversation to any agent who joined. Both halves — the audience filter and the separate room — are required.

The whole mechanism is inert unless whatsappFollowsLeadAssignment is on. With it off, the inbox is fully shared, which is the historical behaviour.

11 — Subsystem: media

Nothing touches the server's disk

All media — library uploads, inbound WhatsApp attachments, support and email attachments — lives on Cloudflare R2. Meta's media URLs expire and require auth headers that a browser <img> tag cannot send, so the inbox serves them through a token-based proxy that reads from R2 and falls back to downloading from Meta on a cache miss.

Five ways these parts talk to each other

Effects hub

Every path that creates a Lead must call queueLeadCreatedEffects, and every path that writes Lead.assignedTo must call queueLeadAssignmentEffects. These are explicit calls, not Mongoose hooks, because the bulk paths use updateMany — which fires no document middleware and would silently skip exactly the case that matters most.

14 — Override analysis

Where one subsystem can countermand another

You asked specifically whether anything overrides anything. The short answer: the architecture is sound — precedence is explicit and single-owner — but there are three places where one subsystem legitimately overrules another, and one of them will surprise you.

By design

Keyword triggers break an agent's takeover

An agent replying sets a 24-hour pause and cancels live sessions. But ladder stages 4–6 bypass the pause and clear it outright. So while a human is actively handling a complaint, a customer who happens to type a word matching a keyword flow will have the bot barge in mid-conversation — and the agent's pause is gone, not just skipped.

Why it is like this A keyword is treated as an explicit new intent from the customer, which is defensible. The surprise is the scope: it clears the pause for everything, rather than letting that one flow run.

Safe by accident

Two lead engines can both fire on one conversation

A flow session running the Smart Lead Engine can also trigger an AI rescue turn, whose lead policy may independently decide to create a lead. Both write through create_lead, which upserts — so the second becomes an update rather than a duplicate.

Assessment Correct outcome, but it holds because the action is idempotent, not because anything coordinates the two engines. Worth knowing before either is changed.

Correct

Out-of-office beats welcome, exclusively

Both auto-replies can qualify on the same message. The engine checks out-of-office first and sets a flag that suppresses the welcome, so a customer messaging after hours gets one message, not two.

15 — Findings

Six open items

Severity reflects customer-visible impact, not effort. Nothing here is architectural — the module's structure is good.

HighW-1

The in-flow AI node silently discards create_lead

The prompt tells the model that create_lead is one of six available actions. The in-flow AI node's handler implements five of them — change_stage, assign_tag, notify_agent, book_appointment, send_template — and has no branch for create_lead. When the model returns it inside a flow, the action is dropped with no log and no lead.

Fix Either implement the branch (routing it through the same policy gate the fallback path uses), or stop advertising the action to that surface. Advertising a capability and silently ignoring it is the worst of both — it also wastes tokens on every call.

HighW-2

"Auto-Create Leads" off does not mean no auto-created leads

Switching the new toggle off does not stop the AI creating leads — it reverts to the previous uncontrolled behaviour, where the model decides on its own and labels the lead however it likes. The control reads as a kill switch and is not one.

Fix Either make off mean off, or replace the toggle with three explicit choices — Never / Let the AI decide / Use my rules. The current label is the problem, not the behaviour.

MediumW-3

Queued and cron work fails silently

Flow delay nodes, no-reply timeouts, the 10-minute follow-up sweep and the 72-hour session expiry all run detached. A failure produces a log line and nothing else — no surfaced error, no retry visible to the tenant. A flow that stops advancing looks to the customer like the business stopped replying.

Fix Emit a counter or health record per scheduled job so a stalled Agenda or a dead cron is visible without reading logs.

MediumW-4

Deleting a tenant orphans their R2 objects forever

Account cleanup purges no object storage and never deletes the media rows. Every tenant deletion leaves inbound media, library assets and knowledge-base files paying rent in R2 with nothing referencing them.

Fix Extend the cleanup service to enumerate and delete by key prefix per tenant, or run a periodic reconciliation against live rows.

MediumW-5

Agent takeover is cleared, not merely bypassed

Detailed in the override analysis. Listed here because the fix is small and the customer-visible effect — a bot interrupting a live human conversation — is not.

Fix Let the triggering flow run without writing chatbotPausedUntil: null, so the agent's pause survives the interruption.

LowW-6

The July audit's High and Medium items are still open

The 2026-07-30 audit found 38 items. Both Criticals and four missing approval checks were fixed the following day; the remaining Highs and Mediums have not been revisited since.

Fix Re-triage that list against the current code — several may already be fixed incidentally.

Metered AI operations

Six operations debit the tenant's credit wallet: ai_fallback, ai_rescue, ai_node, button_mapping, knowledge_index and knowledge_query. Embedding models must have rate rows or they bill at a conservative chat fallback rate — roughly twenty times too high for an upload.

Gates that must be switched on per tenant

  • planFeatures.aiChatbot — the LLM layer
  • planFeatures.knowledgeBase — RAG uploads
  • whatsappFollowsLeadAssignment — lead-based inbox ownership
  • viewWhatsApp per agent — inbox route access

All four default to off or restricted. Most "the feature does nothing" reports resolve to one of these.
